# 17. Планирование фичи в трекере (milestone и issues)

**Опциональность.** Разделы 17 и 18 **не обязательны** для всех задач. Этот процесс включается **только при прямом указании пользователя в промпте** (например: «составь план в Gitea по документации»). Без такого запроса milestone/issues/wiki не являются ожидаемым шагом «по умолчанию».

Ниже — согласованный с модульной архитектурой шаблона порядок **оформления плана** во внешнем трекере (например, **Gitea** через API или веб-интерфейс). Цель — чтобы эпик был прозрачен, а подзадачи можно было закрывать по мере реализации без дублирования «плана в голове».

## Роль milestone

- **Milestone** используется как **контейнер эпика**: в названии и описании фиксируются цель фичи, область работ, **критерии готовности** и краткий список ожидаемых результатов.
- В Gitea отдельной сущности «план проекта» нет; milestone + связанные issues дают тот же эффект для релиза или крупной фичи.

## Разбиение на issues

- Каждая **подзадача** — отдельный **issue**, привязанный к тому же milestone (поле milestone в issue).
- Имена issues лучше начинать с короткого префикса фичи (например, «Профиль клиента: …»), чтобы в списках было видно принадлежность к эпику.

## Рекомендуемый порядок задач в плане

1. **Контракт и модель данных** — поля DTO, эндпоинт(ы), метод, коды ошибок, ограничения (в т.ч. ПДн), при необходимости ссылка на спецификацию или пример JSON.
2. **Интеграция с API и состояние** — клиент `@api`, при необходимости Redux slice, thunk/effects, обработка сетевых и HTTP-ошибок.
3. **Селекторы** — выборки из `state[reducer.name]`, флаги загрузки, ошибка, пустые сценарии; минимум логики в компонентах.
4. **Страница и UI** — `src/pages/**/index.tsx` с `routes`, презентационные компоненты в `src/modules/**/components/`, согласование с темой и существующими паттернами.
5. **Состояния интерфейса** — загрузка, ошибка с возможностью повтора, пусто / «не найдено»; по возможности учитывать доступность (`aria-busy`, `role="alert"` и т.д.).
6. **Качество** — тесты (unit/integration по принятой в проекте практике), **Storybook** (CSF 3, `__stories__`) для новых UI-компонентов; при наличии mock-server — сценарии успех/ошибка/пусто.

Зависимости между задачами явно указывать в теле issue (например: «после согласования контракта из #…»).

## Wiki и статусы

- **Wiki** репозитория можно использовать как **оглавление плана** со ссылками на milestone, issues и позже на PR; таблица «шаг — issue — статус» удобна для обзора.
- Если API wiki недоступен (не инициализирован git wiki, ошибки `refs/heads/master` и т.п.), **не блокировать работу**: продублировать таблицу статусов в **комментарии к ключевому issue** или в описании PR.
