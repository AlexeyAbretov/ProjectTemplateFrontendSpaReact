# 18. Реализация фичи и поставка (ветка, PR, закрытие задач)

**Опциональность.** Ветка `feature/*`, push, PR и закрытие issues в трекере — **не обязательны**, если пользователь **явно не попросил** следовать этому циклу в промпте (например: «отдельная ветка и PR», «по §18»). Архитектура модулей/страниц и проверки качества остаются обязательными по остальной документации и `AGENTS.md`.

Правила ниже дополняют разделы про модули, страницы и тестирование и отражают практический цикл **от ветки до закрытых задач** в трекере.

## Ветка и коммиты

- Разработка ведётся в **отдельной ветке** `feature/<кратко>` (или согласованный в команде префикс), не в `master`.
- Коммиты по возможности **логически связаны** с задачами; в теле коммита или в описании PR допустимо указать `Closes #N` / `Closes #N #M` для автозакрытия issues при слиянии в ветку по умолчанию (если так настроен сервер).

## Соответствие архитектуре шаблона

- **Страницы** — только через `src/pages/<page>/index.tsx` с экспортом `routes`; модуль не содержит знаний о путях, кроме случаев навигации через `CustomEvent` по соглашению проекта.
- **Модули** — `src/modules/<module>/index.ts`; при Redux экспорт `reducer` с полями `name` и `value`; **ключ в store** = `reducer.name`; селекторы читают `state[reducer.name]`.
- **API** — через общий клиент `@api`, без дублирования базового URL; ошибки `ApiError` не «проглатывать» без явной продуктовой логики (мок при недоступном сервере — осознанное исключение, как в существующих модулях).
- **UI со сменой идентификатора в маршруте** — избегать отображения **устаревших данных** предыдущего запроса: при новом запросе очищать соответствующие поля state в `pending` или эквивалентной фазе.

## Тесты и регрессия

- Любой новый код, который тянет **Router** (`Link`, `useParams`, …), должен учитываться в тестах: оборачивать рендер в **`MemoryRouter`** / `Routes`, как в тестах страниц и модулей с навигацией.
- После изменений прогонять **`npm run lint`**, **`npm test`**, **`npm run test:coverage`** (с учётом `coverageThreshold` в `jest.config.js`) и **`npm run build`**.

## PR и трекер

- После push создать **pull request** в целевую ветку (обычно `master`) с кратким описанием изменений, ссылкой на **milestone** и перечислением закрываемых issues.
- **Закрытие issues** — по политике команды: либо вручную после ревью, либо автоматически при merge с ключевыми словами в коммите/описании PR.
- Если wiki не обновлялась, **актуализировать статусы** в комментарии к issue или в описании PR (таблица «задача — выполнено»).
